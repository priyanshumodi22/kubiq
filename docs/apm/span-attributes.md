# Span detail and storage compatibility

The span inspector displays all recorded attributes for any supported storage adapter. MongoDB stores its attribute map; SQL and ClickHouse store equivalent JSON. Changing storage does not change the producer's captured fields.

The controlled `kubiq-backend` profile uses explicit repository spans because the bundled backend cannot rely on driver auto-instrumentation. Earlier SDK 1.1.0 spans intentionally contained only `db.system` and the repository operation. SDK 1.1.1 permits additional bounded diagnostic metadata: `db.system.name`, `db.namespace`, `db.collection.name`, `server.address`, `server.port`, `code.namespace` and `code.function.name`. The backend derives database/host/port and physical collection names from the actual registered Mongoose model and connection. Config operations use their config model, rather than incorrectly claiming to read the services collection. The operation remains a repository operation; it is not presented as an intercepted wire-level MongoDB command.

Request SERVER spans separately carry normalized HTTP route, method and response status. Select the request row to inspect those fields; a database child has its own database attributes. Existing historical spans are unchanged: details that were never captured cannot be reconstructed safely. New requests after deployment receive the enriched fields.

Passwords and other credentials, connection URI user-info, cookies, HTTP request/response bodies and database result documents remain excluded. Following the explicit request for Instana-style query detail, `KUBIQ_TRACING_QUERY_DETAILS=true` additionally records bounded MongoDB command documents and SQL statements/bound parameters. Non-credential query values are included; this supersedes the earlier metadata-only profile. Regression fixtures verify the same attribute values survive MongoDB, MySQL, MariaDB and ClickHouse storage.

The controlled MySQL/MariaDB repositories now use the same request-scoped repository tracing contract. Their server/port/database come from the resolved mysql2 pool configuration, rather than environment-variable guesses (different repository defaults can differ). Multi-table or cached repository work is not falsely labeled as a particular SQL statement or execution plan. The detail panel normalizes both modern and legacy OpenTelemetry database fields, so third-party MySQL/MongoDB producers retain their more specific command/table/result metadata when supplied.

The inspector groups service/operation/type/timing, database target, HTTP context, code/error metadata and all raw attributes. Its interpretation is storage-independent. Missing query text, row counts, server-side plans or stack traces are never fabricated from a repository method name.

The relationship section identifies the loaded parent operation and direct child count. Own duration subtracts the union of loaded child intervals, clipping them to the parent and avoiding double subtraction for overlapping calls. It is wall-clock time from the loaded trace, not CPU usage or a server-side query execution plan.

Design reference: IBM's [Instana trace and call-detail exploration](https://ibm.github.io/instana-techxchange/labs/instana-v2/explore-instana/explore/) describes selecting calls for contextual details. This panel follows that interaction model; it does not claim Instana agent feature parity or fabricate missing call data.

Actual MongoDB command spans use driver command-monitoring events and their real completion/failure events. MySQL/MariaDB query, execute and transaction calls are wrapped at the Promise pool/connection boundary, preserving arguments, owning this, return values, error identity, connection release and replacement pools. They create distinct CLIENT child spans under repository context, with actual operation duration, result counts where supplied, error codes, database and target facts. Initialization, background work, excluded requests and telemetry persistence do not create these spans. MongoDB command monitoring is enabled only for the opt-in shared application connection; it requires no additional database privileges.

Redaction happens before queueing/export. Nested password/token/key fields and serialized configuration are masked. Known credential environment values and credential URLs are masked. Credential-related SQL and its parameters, stored procedure calls, and opaque configuration writes may be fully redacted because individual secret positions cannot always be inferred safely. The panel shows explicit redaction markers. HTTP URL queries and response bodies remain outside capture. Old spans cannot gain missing statements retrospectively.
